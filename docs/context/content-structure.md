# 칸과 파일 규격

**언제 읽나** — 항목을 추가하거나 고칠 때. front matter를 쓸 때. 목록을 늘릴 때.
새 섹션을 만들 때. **이 파일만 읽으면 코드를 안 봐도 항목을 만들 수 있다.**

## 칸

| 경로 | 내용 |
|---|---|
| `content/me/` | "나" — 형식 없는 항목이 시간순으로 쌓임 |
| `content/work/` | "만든 것" |
| `content/writing/` | "글" |
| `content/reading/` | "읽은 것" — 책과 그에 대한 생각 |
| `content/watching/` | "본 것" — 영화·드라마 |
| `app/` | 화면. 섹션을 추가할 때 말고는 손댈 일이 없다 |
| `app/threads/` | 「갈래」 — 다섯 칸을 가로지르는 축. 내용은 앞머리의 `strand`에서 |
| `app/map/` | 「지도」 — 사이트 전체를 한 장에. 뻗어나간 그림도 여기 |
| `lib/content.ts` | 마크다운을 읽어 페이지로 넘기는 유일한 통로 |

항목을 추가하는 방법은 **두 가지**다. 둘 다 코드를 고치지 않는다.

1. `content/<섹션>/`에 `.md` 파일을 하나 넣고 푸시한다
2. **`npm run studio`** — 입력 화면에서 쓰고 저장하면 파일이 만들어지고,
   확인 화면에서 버튼을 누르면 올라간다 (→ `build-and-deploy.md`)

## 앞머리 (front matter)

`title`, `date`만 필수. 나머지는 선택 —
`tag`, `summary`, `author`, `link`, `then`, `about`, `strand`, `read`, `list`, `unread`.

- 날짜는 반드시 `YYYY-MM-DD`. YAML이 Date 객체로 바꿔버리므로 `lib/content.ts`의
  `toISODate()`를 거쳐야 한다
- `work`, `writing`, `reading`의 파일명은 URL이 되므로 **영문 소문자·숫자·붙임표만** 쓴다
  (`me`는 상세 페이지가 없어 자유)

### `about` — 글이 다루는 시기

`date`는 **글을 쓴 날**이고 `about`은 **언제의 나에 대한 글인가**다. 2021년 이야기를
2026년에 적을 수 있으므로 둘은 다르다. 지금은 「나」에서만 뜬다.

```yaml
date: 2026-09-09        # 쓴 날
about: "2020–2022"      # 다루는 시기 → 「2020–2022년에 대해」
```

- 연도 하나든 범위든 자유. **범위는 반드시 따옴표로 감싼다** — YAML이 `2021-2022`를
  날짜로 넘겨다볼 여지를 없앤다
- 안 적으면 화면에 아예 안 나온다. 지금 이야기를 쓸 때는 적지 않는다
- 앞으로 쓰는 글에 이걸 안 달면 전부 쓴 날짜만 달고 쌓여서, 나중에 또 발굴해야 한다

### `strand` — 이 항목이 걸리는 갈래(관심사)

섹션은 **매체**로 나뉘지만 생각은 **관심사**로 묶인다. 음식에 대한 책과 음식 앱이 다른
섹션에 있어도 같은 갈래로 이어진다.

```yaml
strand: 먹는 일, 재는 일        # 쉼표로 여럿
```

- 값은 **「나」의 "지금 관심이 벌어져 있는 자리들"에 적힌 아홉 개 이름을 그대로** 쓴다.
  목록은 `lib/content.ts`의 `STRAND_NAMES`에 있다. **새 이름을 지어내지 않는다**
- **억지로 다 채우지 않는다.** 아홉 갈래 어디에도 안 맞으면 안 붙인다.
  비어 있는 갈래가 있어도 그대로 둔다
- 목록(`list: true`)에는 안 붙는다. `getByStrand()`가 낱개 글만 훑는다
- 인간관 관련 **열 번째 갈래는 아직 후보이며 확정되지 않았다** (2026-09-11 기준)

### `then: true` — 그때 적어둔 것을 옮긴 글

화면에 *"2021년에 적어둔 것을 옮겼습니다"* 가 붙는다(연도는 `date`에서).
**발굴로 올라오는 글에는 반드시 붙인다.**

이건 **시점을 밝히는 용도이지 "지금과 다를 수 있다"는 단서를 다는 용도가 아니다.**
옛 글 대부분은 지금과 이어져 있다. 이질적인 것은 올리기 전에 걸러야지, 올려놓고 각주로
면책할 일이 아니다.

### `read` — 책을 읽은 때

`date`는 글을 쓴 날, `read`는 책을 읽은 때. 두 때가 갈리는 책의 판별자다.
→ 쓰는 법은 `reading.md`

## 목록 — 앞머리에 `list: true`

본문 없이 제목만 쌓이는 목록(읽은 책 133권 같은 것)은 낱개 글이 아니라 **파일 하나에 표**로
넣는다. 수백 권을 개별 파일로 만들면 빈 상세 페이지가 수백 개 생긴다.

앞머리에 `list: true` 한 줄만 넣으면 목록이 된다. **목록을 늘릴 때도 코드를 고치지 않는다.**

```markdown
---
title: 대학원에서 읽은 교재
date: 2026-09-10
summary: 수업에서 쓴 책들
list: true
---

(안내문)

| 제목 | 지은이 | 연도 |
| --- | --- | --- |
| 책 이름 | 지은이 | 2024 |
```

- 한 줄에 하나. 둘째·셋째 칸은 비워도 된다. 넷째 칸부터는 무시되므로 열을 늘려도 안 깨진다
- **셋째 칸은 목록마다 뜻이 달라도 된다.** 군대 목록은 연도로, 교재 목록은 과목으로 쓴다.
  화면에는 오른쪽에 작게 붙는다
- 제목에 세로줄(`|`)은 쓰지 않는다
- 파서(`getList()`)는 **어떤 입력에도 예외를 던지지 않는다.** 줄이 깨지면 그 줄만 빠진다
- **`unread: true`** — 이 목록의 책은 아직 안 읽은 것이다(「읽고 싶은 책들」).
  "읽은 책이 몇 권"을 셀 때 빠진다. 안 붙이면 읽은 것으로 센다
- 같은 제목으로 낱개 글을 쓰면 목록 행이 **자동으로** 그 글로 이어진다
- 낱개 글과 목록이 `[slug]` 경로를 함께 쓴다. 화면만 다르게 그린다

### `_`로 시작하는 파일은 항목이 아니다

`_notice.md`처럼 여러 화면이 함께 쓰는 조각을 둔다. 낱개 글로 잡히지 않고 주소도 생기지 않는다.

- **`_about.md`** — 섹션 화면 끝에 붙는 설명. `getNotice(dir, "about")`으로 부른다

### 목록을 낱개 글보다 먼저 둔다

2026-09-11에 「읽은 것」에서 낱개 글 여섯 편이 위에 큰 제목으로 떠서
*"이것들이 대표작처럼 보인다"* 는 지적을 받았다. 실제로는 198권 중 글이 붙은 것이 여섯일 뿐
고른 것이 아니다.

**분량이 많은 쪽을 먼저 보여주고**, 낱개 글 묶음 위에는 그것이 선별이 아님을 한 줄로
밝힌다 (`.blockhead`).

**같은 종류의 실수가 문장 아닌 배치에서도 난다** — 채팅에서 나온 질문 하나에 제목을 달아
독립 항목으로 세우면 그 배치 자체가 "이게 내 대표 주제다"라는 주장이 된다.
2026-09-10에 실제로 벌어져서 다섯 항목을 하나로 합쳤다. (→ CLAUDE.md의 1인칭 근거 규칙)
